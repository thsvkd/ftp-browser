# 핸드오프: 탐색기 메뉴 버그 수정 + 포커스 모델 단일화 (선택 = 포커스)

Explorer v2 묶음의 첫 스펙이다. 결정은 `.omc/plans/explorer-v2-decisions.md`의 §A(버그)와 §B(포커스 모델)에서 왔고, 사람과 합의가 끝났다.
이 문서가 테스트·구현의 유일한 입력이다. 이 문서에 없는 케이스는 완료 범위 밖이다. 케이스를 추가·병합·재해석하지 말 것.
`[사용자]`로 표시되지 않았어도 R1에서 확정된 항목(M1~M3, F1~F9)은 다시 열지 않는다. 이 문서가 스스로 고른 것은 **미결(권장안 적용)** 으로 따로 표시했다(§2 끝, 보고용 목록은 §15).

작업 유형(R0): **버그 수정 2건(메뉴 열자마자 닫힘, 선택 시 아이콘 축소) + 소규모 UI 모델 변경(포커스 표시 3상태 통합, 선택 쓰기 경로 전부를 순수 함수로)**. main·IPC·공유 타입 변경 없음. 새 i18n 키 없음.
슬라이스(§12)마다 그 슬라이스의 테스트를 먼저 세워 RED를 보고 GREEN으로 만든다. 끝으로 실제 앱에서 R3 실측(§13)을 한다.

기준 커밋: `670eb0f`(v1.3.0). 선행 스펙: `docs/handoff/explorer-shelf.md`(이하 "shelf 스펙"). 이 문서는 shelf 스펙의 D24와 §11 기준선 #1~3·#7 일부, Test-775·776·791·794 일부를 **대체**한다(§7).

## 3. 동작 상세

### 3-1. 메뉴를 연 click이 닫지 않는다 (M1)

```
click(＋)  window capture ─ (ItemMenu 아직 없음)
           … React 루트(bubble): onClick → setMenu → 동기 렌더 → effect: 리스너 등록
           document(bubble): ItemMenu의 click 리스너 ← 같은 이벤트가 도착
```

고침 후: `window` capture 리스너(`mark`)도 effect에서 등록된다. 같은 이벤트는 이미 capture를 지났으므로 `captured`가 그 이벤트가 아니다 → `onClick`이 닫지 않는다.
이후의 click은 `mark`(capture) → `onClick`(bubble) 순으로 불려 `captured === e`가 되고, 메뉴 밖이면 닫는다.

주의: 코드 모양은 `onContext`(:245-247)와 같다. `inside(e.target)` 검사는 그대로(하위 메뉴 `subRef` 포함). Esc·blur·scroll 닫기는 건드리지 않는다.

### 3-2. 선택 상태 전이표 (순수 모델)

| --------------------------------------- | -------------------------------------------------------------------------------------------------------- |

### 3-3. 키보드로 쓰는 법 (커서를 지운 뒤)

- 목록에 포커스가 오면(Tab, 탭 전환 뒤 자동 포커스) 선택이 없을 수 있다. **첫 ↓/→/Home/PgDn은 첫 항목, End는 마지막 항목을 고른다.** 그 뒤부터는 선택이 곧 위치다.
- 여러 개를 고르려면 Shift+화살표(연속) 또는 Ctrl+클릭/체크 원(떨어진 것). 키보드만으로 떨어진 항목을 고르는 길은 **Ctrl+Shift+화살표(범위 더하기) 뿐이고**, 커서만 옮기고 Ctrl+Space로 담던 방식은 없어진다.
- Enter/Space(미리 보기)/F2/Alt+Enter(속성)는 `focus` 항목 하나에 작동한다(다중 선택에서도 지금과 같이 `focus` 하나). Delete·Shift+S·메뉴 키의 대상은 선택 **전체**다.
- 이동 키는 이동 뒤 `ensureVisible`로 스크롤한다(변경 없음).

### 3-4. `aria-activedescendant` 갱신 (D24 대체)

shelf 스펙 D24의 "포커스 커서는 `aria-activedescendant`"를 다음으로 바꾼다.

> 목록(`role="listbox"`)의 `aria-activedescendant`는 **선택된 항목 중 작업 대상인 항목(`Tab.focus`)** 의 `optId`다. 선택이 없거나 그 항목이 필터·찾기로 숨겨졌으면 속성을 두지 않는다. 가리키는 `option`은 언제나 `aria-selected="true"`다.

- 키보드 이동·클릭·Shift 범위·마퀴·라이트박스 이동(`selectOnly`) 모두 같은 규칙으로 갱신된다. 별도 코드 경로는 없다(`focusPath`에서 계산).
- 가상화 때문에 가리키는 요소가 DOM에 없을 수 있다. 이동 키가 `ensureVisible`로 먼저 스크롤하므로 정상 경로에서는 렌더된다. 이 점은 지금과 같고 이번 범위 밖이다.
- `optId`는 `lib/explorerLayout.ts:21`을 쓴다. 테스트는 id 문자열을 하드코딩하지 않고 `optId`를 import한다 (split-view 스펙이 패널 id를 접두로 붙일 수 있다).

## 5. 기각한 대안

- **메뉴를 여는 호출처마다 `setTimeout(0)`/`stopPropagation`** — 호출처가 늘 때마다 같은 함정이다(M2). 기각.
- **닫기 리스너를 `window` capture 하나로 옮기기** — 같은 증상을 풀지만 닫기가 대상 핸들러보다 **먼저** 돌아 "메뉴 A가 열린 채 버튼 B를 누르면 A 닫힘 → B 열림" 순서가 바뀌고, 이미 있는 contextmenu 방어와 두 가지 방식이 섞인다. 결정 기록이 정한 "contextmenu 방어를 click에도"로 간다. 후속으로 합칠 수는 있다.
- **`Tab.focus` 필드 삭제, 선택만 남기기** — 키보드 이동의 출발점과 Enter의 대상을 `sel.at(-1)`로 대신해야 하는데, Shift 범위의 끝과 클릭한 항목이 다를 수 있어 의미가 흔들린다. 불변식으로 묶는 쪽이 작다(F1). 기각.
- **Ctrl+화살표를 무동작으로 막기** — 사용자가 눌러도 아무 반응이 없어 고장처럼 보인다. 일반 이동으로 둔다(F3, 미결 권장안).
- **빈 선택 상태용 컨테이너 포커스 링 신설** — "포커스 표시 3상태" 결정과 부딪히고 새 시각 요소를 만든다(F9). 기각, 후속 과제.
- **목록이 포커스를 잃으면 선택을 흐리게(`--selin`) 유지** — 사람이 폐기했다(F2·F8).
- **Ctrl+Space 폐기** — Ctrl+클릭의 키보드 대응으로 남긴다. 커서가 없어도 `focus` 항목을 토글하는 뜻이 선다(F3).
- **삭제가 실패하면 선택을 유지하기** — 사용자 눈에는 더 친절하지만 지금 동작(Test-81·87이 `sel: []`을 고정)을 바꾸는 별도 결정이다. 이 스펙은 `focus`만 I2에 맞춰 같이 푼다(F10). 기각, 후속 과제.
- **Ctrl+A가 숨은 `focus` 대신 보이는 마지막 항목을 `focus`로 삼기** — Enter가 갑자기 다른 항목을 여는 효과가 생기고 "Ctrl+A는 `focus`를 건드리지 않는다"는 F3의 말과 어긋난다. `null`이 I1·I2를 지키는 가장 작은 값이다(Q5).
- **I1을 각 호출처에서 `focus` 필드를 같이 써서 지키기** (`patch({ sel: paths, focus: … })`) — 호출처마다 규칙이 갈라진다. 순수 함수 하나(`selectAll`)에서 한 번 정한다(F10).
- **선택 해제 시 마퀴 말고 `click` 이벤트로 빈 곳 처리** — 마퀴가 이미 `mousedown`에서 비수정자 빈 곳 클릭을 처리한다. 두 군데에서 처리하면 이중 호출이다. 기각(F5).

## 8. 구현 함정

1. **기존 메뉴 테스트가 버그를 못 잡은 이유, 그리고 jsdom으로 RED가 되는 것/안 되는 것.** `act()` 안 `fireEvent`는 이벤트가 끝난 **뒤에** 렌더·effect를 흘려 넣어 리스너가 늦게 붙는다. 새 테스트는 ① 네이티브 `dispatchEvent`를 `act` 밖에서 보내고 ② 그 전에 `globalThis.IS_REACT_ACT_ENVIRONMENT = false`로 두며(테스트 끝에 복구) ③ 비동기 대기는 `flush()`(act를 씀)가 아니라 `await new Promise((r) => setTimeout(r, 0))`로 한다. **먼저 현재 코드에서 RED인지 확인한다.**
   - **동기 호출처(Test-846·848·849)는 jsdom에서 RED가 된다.** React 19에서 이산 이벤트의 `onClick` 안 `setState`는 이벤트 끝에서 동기로 렌더·effect까지 끝나므로 `document` 리스너가 같은 이벤트를 받는다. 만에 하나 재현하지 못하면 Test-846처럼 네이티브 리스너 안에서 `flushSync(() => root.render(<ItemMenu …/>))`로 같은 순서를 만든다(`flushSync` 대체는 `ItemMenu`를 직접 그리는 Test-846에서만 가능하다. 호출처 코드를 고치지 못하는 Test-848·849에는 쓸 수 없다. M2).
   - **`＋`(Test-850)는 jsdom에서 RED가 되지 않는다. 이 스펙의 유일한 RED 예외다.** 실제 Chromium은 사용자 click의 리스너 사이에서 마이크로태스크 체크포인트를 돌려 `await loadPlaces()` 뒤의 `setMenu`·렌더·effect가 전파 **도중**에 끝난다(M1 근거). jsdom의 `dispatchEvent`는 테스트의 JS 스택 안에서 도므로 그 호출이 끝나기 전에는 마이크로태스크가 돌지 않아, 현재 코드에서도 메뉴가 열려 남는다(React 19.2.4 + jsdom 30에서 `onClick: () => setA(true)` 메뉴는 자기 닫힘, `onClick: async () => { await Promise.resolve(); setB(true) }` 메뉴는 열려 남음을 비평 단계에서 확인했다. 구현자는 같은 실험을 다시 돌려 본다). 그래서 Test-850은 **GREEN-before 회귀 방어**이고, `＋` 고침의 RED 증거는 R3 (a)의 실제 입력 이벤트다(§13-1). 구현자는 Test-850을 현재 코드에서 돌려 GREEN임을 확인하고 그 사실을 PR에 적는다. "RED가 아니니 테스트가 틀렸다"며 고치지 않는다.
   - 비동기 경로의 일반 메커니즘(마운트가 전파 도중에 일어남)은 Test-846이 `ItemMenu` 수준에서 이미 고정한다.
2. **마킹은 이벤트 객체 동일성이다.** `captured === e`. 마킹 리스너는 `window`의 **capture** 단계여야 한다(`addEventListener(type, mark, true)`). cleanup에서 같은 인자로 `removeEventListener`.
3. **`ItemMenu` 안쪽 클릭은 그대로 열어 둔다.** `inside(e.target)` 검사를 지우지 말 것(Test-110·Test-109 쌍).
4. **`I1`·`I2`는 순수 함수가 지키고, 쓰기 경로는 전부 거기를 지난다(F10).** 컴포넌트가 `patch({ sel/anchor/focus })`를 직접 쓰지 않는다. `patch(selectMany(…))`·`patch(selectAll(…))`·`patch(clearSelection())`·기존 `patch(clickSelect/moveFocus/toggleSelect(…))`만 쓴다. 직접 쓰기가 남던 곳은 셋이었다: `askDelete` finally(:339, `focus`가 남아 삭제 실패 뒤 `aria-activedescendant`가 선택 해제된 항목을 가리킨다), Ctrl+A(:614)와 메뉴 "모두 선택"(:502)(`focus`가 필터로 숨으면 선택 밖에 남는다). 테스트 하네스의 `renderExplorer(loc, { focus })`처럼 `sel` 없는 `focus`를 주는 호출은 쓰지 말 것.
5. **마퀴 `setSelection`은 mousemove마다 부른다.** `selectMany`는 `Set`으로 중복을 거르는 O(n) 이내여야 한다. 가산 모드의 `[...base, ...names]`는 겹침이 있어 지금도 `sel`에 중복이 들어간다 → `selectMany`가 걸러낸다(Test-854).
6. **`targetOf(cur)` 변경을 놓치지 말 것.** `cur` 폴백을 남겨 두면 코드는 무해하지만 "선택이 없어도 대상이 있다"는 낡은 모델이 남는다. 지운다(F7).
7. **오른쪽 클릭의 `selectOnly`(Explorer.tsx:664)와 라이트박스 `selectOnly`(:884)는 그대로다.** I1을 이미 지킨다.
8. **`Tile`의 체크 원(:59-65)**: `p.selected ? … opacity-100`이 이미 있으므로 `p.cursor && p.listFocused && 'opacity-100'`만 지우면 된다. 호버 때 보이는 동작(`group-hover:opacity-100`)은 hover 상태의 일부로 남는다.
9. **split-view와의 관계.** 분할 뷰가 생기면 패널마다 자기 `sel`/`focus`를 가지고 비활성 패널의 선택도 같은 `focus` 색이다. "어느 패널이 활성인가"의 시각 표시는 `docs/handoff/split-view.md`가 정한다(경로 막대 상단 바 등). 이 스펙은 항목 색을 활성 여부와 무관하게 만들었을 뿐이다. 또 `optId(path)`의 DOM id 중복은 split-view가 해결한다.
10. **macOS의 Ctrl+화살표**는 OS(Mission Control)가 먼저 가져갈 수 있다. 앱에 닿지 않아도 F3의 Ctrl 처리와 충돌하지 않는다.

export const clearSelection = (): SelectionState => ({ sel: [], anchor: null, focus: null })

export function selectMany(state: SelectionState, paths: readonly string[]): SelectionState {
  const sel = [...new Set(paths)]
  if (!sel.length) return clearSelection()
  const anchor = state.anchor && sel.includes(state.anchor) ? state.anchor : sel[0]
  return { sel, anchor, focus: sel[sel.length - 1] }
}
export function selectAll(state: SelectionState, paths: readonly string[]): SelectionState {
  const sel = [...new Set(paths)]
  if (!sel.length) return clearSelection()
  return {
    sel,
    anchor: state.anchor,
    focus: state.focus && sel.includes(state.focus) ? state.focus : null
  }
}

## 11. 위험과 후속 과제

**위험**

- **키보드만으로 떨어진 항목을 고르는 길이 줄어든다**(F3). 커서를 옮겨 Ctrl+Space로 담던 방법이 없어지고, Ctrl+Shift+화살표(범위 더하기)와 Ctrl+클릭만 남는다. 사람이 승인한 모델의 직접 결과다.
- **선택이 없는 채 목록에 포커스가 있을 때 시각 신호가 없다**(F9). R3 (c)에서 눈으로 본다.
- **고대비(forced-colors)에서는 `[aria-selected='true']` 윤곽선이 유일한 표시**다. 호버/선택 구분이 사라질 수 있다. R3에서 확인한다.
- **메뉴를 여는 새 호출처가 생기면** `ItemMenu` 하나만 믿는다(M2). 그 방어가 깨지면 모든 메뉴가 다시 죽는다. Test-846·848~850이 지킨다.
- **`Tab.sel`에 숨은 경로가 남는다**(후속 과제와 같은 뿌리). Ctrl+A 뒤에는 보이는 경로만 `sel`에 들어가므로 이 스펙이 만드는 새 어긋남은 없다. 필터를 바꾸기 전에 잡아 둔 `sel`이 숨은 채 남는 것은 지금과 같다.
- **분할 뷰와의 접점**(함정 9): 이 스펙은 항목 색에서 활성 패널 구분을 없앴다. split-view 스펙이 다른 표시를 정해야 한다.

**후속 과제(이번 범위 밖)**: 빈 선택 상태의 컨테이너 포커스 신호(Q3), 닫기 리스너를 `window` capture 하나로 통합(§5), Enter가 다중 선택 전체를 여는 동작(지금은 `focus` 하나), 필터·찾기로 숨은 항목이 `sel`에 남는 문제(`sel`에서 숨은 경로 정리), 같은 `ItemMenu` 인스턴스 안에서 메뉴를 바꾸는 click(아래).

- **경로 막대의 정렬 메뉴 ↔ "…"(숨은 조각) 메뉴 전환**: `PathBar`는 두 메뉴에 key 없는 `ItemMenu` 하나를 쓴다. 인스턴스가 마운트된 채 남아 리스너가 이미 붙어 있으므로, 정렬 메뉴가 열린 채 "…"를 누르면(또는 반대) 그 click이 capture에서 표시되고 `setMenu(새 메뉴)` 뒤 기존 인스턴스의 document 바깥 닫기가 `setMenu(null)`을 불러 아무 메뉴도 열려 있지 않다(§5의 "A 닫힘 → B 열림"과 어긋남). 고치기 전에는 두 메뉴 모두 아예 열리지 않았으므로 회귀는 아니다. M2가 호출처 우회를 금지하므로 이 스펙에서는 고치지 않는다. 후속 선택지: `PathBar`의 `ItemMenu`에 메뉴 종류별 key를 줘 다시 마운트하거나, 같은 이벤트 안에서 `items`/`label`이 바뀌었으면 `ItemMenu`가 바깥 닫기를 건너뛴다. 어느 쪽이든 네이티브 click 한 번으로 정렬 → "…" 전환을 확인하는 테스트(Test-848과 같은 `flushSync` 체크포인트)를 더한다.

## 16. R3 결과 (2026-10-13, macOS, 구현 세션)

**구동**: 공유 `node_modules`에 이 브랜치의 `@modelcontextprotocol/*`가 없어 `npm run build`(typecheck 포함)는 그 모듈 오류로 멈춘다. 그래서 `npx electron-vite build`로 `out/`을 만들고, `out/node_modules`에 빈 MCP 스텁(에이전트 접근은 기본 꺼짐이라 쓰이지 않는다)을 두고 Electron 바이너리를 `--remote-debugging-port`·스크래치 `--user-data-dir`로 실행해 CDP로 조작했다(`Input.dispatchMouseEvent`/`dispatchKeyEvent` 실제 입력). 서버 대신 로컬 탭(깊은 경로의 `photos`: 폴더 `locked`·`sub`, 파일 `f00`~`f13.txt`)을 썼다. UI 로캘은 OS를 따라 한국어였다.

**jsdom 메모(§8 함정 1 보충)**: 이 환경(React 19 + jsdom)에서는 동기 호출처도 `act` 밖 `dispatchEvent`만으로 재현되지 않았다. React가 이산 이벤트의 SyncLane 렌더를 마이크로태스크로 미루고, jsdom은 리스너 사이에 마이크로태스크 체크포인트를 돌지 않기 때문이다. 그래서 Test-848·849는 `document.body`의 버블 리스너에서 `flushSync()`를 불러 브라우저의 체크포인트 시점을 흉내 낸다(호출처 코드는 그대로, M2). 이렇게 하면 고치기 전 코드에서 RED였다. Test-850(＋, 비동기)은 스펙대로 고치기 전에도 GREEN이었다(실행 출력 확인).
