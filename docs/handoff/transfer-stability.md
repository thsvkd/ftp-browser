# 핸드오프: 전송 안정화 후속 묶음(실패 다운로드 정리 · 425/421 한도 학습 · MCP 저장 서버 대상)

`transfer-retry-disconnects.md` R3에서 남은 후속 과제와 `same-host-accounts.md` SH14의 후속을 한 묶음으로 처리한다. 네 가지다.

1. 실패로 끝난 일반 다운로드가 받다 만 로컬 파일을 남기지 않는다.
2. 데이터 연결까지 연결 수로 세는 서버의 425를 전송 풀이 연결 수 한도(`LIMIT`)로 배운다. 그래서 몰림 한 번에 재시도 3회를 다 쓰지 않는다.
3. 세션 도중 명령 응답으로 오는 421을 같은 횟수 제한으로 재시도하고, 풀은 이것도 `LIMIT`로 본다.
4. MCP에서 저장 서버 id·별칭·호스트는 **그 저장 행의 사용자 연결로만** 이어진다(MC18 ①의 물러서기 삭제).

출처는 다음 셋이다. `transfer-retry-disconnects.md` §9 후속 과제와 §11 관찰 2·R3 (a), 그 문서 §5 둘째 항목(425를 풀 한도로 학습하기), 그리고 `same-host-accounts.md` SH14·§13 후속이다. `[사용자]`는 사람이 네 항목을 모두 하기로 고른 것이다. 이 문서는 그 결정을 구현 단위로 내린 **유일한 입력**이다.
이 문서에 없는 케이스는 완료 범위 밖이다. 케이스를 추가·병합·재해석하지 말 것.

작업 유형(R0): **버그 수정 2개(①·④) + 동작 변경 2개(②·③, main 전송 스케줄링)**. 렌더러·IPC 채널·i18n·DB 변경은 없다. MCP 도구 수(12)와 스키마도 그대로다.
슬라이스는 셋이다(§8). 슬라이스마다 §7의 테스트를 먼저 세워 RED를 본 뒤 GREEN으로 만들고, 끝에 실제 앱에서 R3 실측(§9)을 한다.

## 1. 바꾸는 것

### 1-1. 실패한 다운로드의 받다 만 로컬 파일(①)

지금 일반 다운로드의 로컬 파일 정리는 다음과 같다.

| 경로                                                 | 취소                                                | 최종 실패                                                                                    |
| ---------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 한 스트림(`transfer` → `fileOps.download`)           | 지운다(`TransferQueue.ts:567-573`, `removePartial`) | **남는다.** `fail()`(`:1001-1008`)은 파일을 건드리지 않는다. R3 (a)에서 4 MiB 두 개가 남았다 |
| 한 스트림 재실행(`oneStream`, REST 무시·거부 뒤)     | 위와 같다                                           | 위와 같다(구간 항목이 아니다)                                                                |
| 분할(`startSegmented` → 구간 항목, LAN 한 구간 포함) | 지운다(`closeSegmented`, `:828-831`)                | 지운다(`closeSegmented`의 `failed` 분기 `:844-848`, 크기 불일치 `:838-842`)                  |
| 로그인 실패 연쇄(`failPending`, `:962-967`)          | 해당 없음                                           | 대기 항목을 그 오류로 실패시킨다. 앞선 시도(재시도 대기)가 연 파일이 있으면 **남는다**       |

`downloadToFile`(`FtpFileOperations.ts:113-148`)은 오류가 나면 크기 0인 파일만 지운다(basic-ftp와 같다). 그 밖의 바이트가 있는 파일은 남는다.

**받다 만 파일에 기대는 이어받기 경로는 없다(근거).**

- 한 스트림은 언제나 처음부터 쓴다. `downloadToFile`은 `'w'`(배타적이면 처음만 `'wx'`)로 열고(`:119`) `downloadInto(client, writer, remotePath)`를 `startAt` 없이(0) 부른다. REST를 보내지 않는다.
- 분할은 `open(localPath, 'w')` 뒤 `truncate(size)`로 다시 만든다(`TransferQueue.ts:648-654`). 구간의 REST 오프셋은 이번 실행에서 만든 `SegmentRange`에서만 온다.
- 자동 재시도(`retryOrFail`, `:974-999`)와 사용자 재시도(`retry`, `:273-300`)는 `transferredBytes = 0`이고 다음 시도가 파일을 다시 연다(위 두 규칙).
- 다른 곳에서는 `fileOps.download`를 부르지 않는다(`grep`: `TransferQueue.ts:585`뿐). `src` 전체에서 이어받기(`resume`)는 소켓 흐름 제어(`segmentWriter.ts:187`)뿐이다.
- `sparseFile.ts`의 `markSparse`는 분할이 연 같은 파일(`localPath`)에 희소 플래그만 건다(`TransferQueue.ts:653`). 따로 쓰는 임시 파일이나 `.part` 파일은 없다. 그래서 "희소·임시 파일"의 정리는 분할 경로의 기존 정리(`closeSegmented`)가 이미 맡고 있다.

그래서 최종 실패에서 지워도 잃는 것이 없다. 대신 **이 작업이 열지 않은 파일은 지우면 안 된다**(TS3).

### 1-2. 425·421과 전송 풀(②·③)

basic-ftp 6.2.0이 던지는 모양과 지금 처리는 다음과 같다(앞 문서 §1의 E3·E4·E5와 같은 이름).

| #   | 상황                                                                    | 던지는 것                                                                                                                 | 지금                                                                                             | 바뀐 뒤                                                     |
| --- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| E3  | 수동 모드를 이미 고른 클라이언트의 PASV 거부                            | `FTPError`, `code: 425`                                                                                                   | 재시도 3회(TR2). 클라이언트는 그대로 다시 쓴다(`releaseAfterError`)                              | 다른 풀 연결이 열려 있으면 `LIMIT`(TS8). 아니면 지금 그대로 |
| E4  | 새 클라이언트의 첫 전송에서 EPSV·PASV가 모두 실패, 마지막이 425         | `Error("None of the available transfer strategies work. Last error response was 'FTPError: 425 …'")`(`Client.js:729-746`) | 재시도 3회. 클라이언트는 버린다                                                                  | 위와 같다                                                   |
| E6  | 세션 도중 명령(RETR·STOR·PASV 등)의 응답이 421, 서버가 제어 연결을 닫음 | `FTPError`, `code: 421`(`FtpContext.js:311`. 뒤이은 FIN은 `_closingError`만 남기고 작업은 421로 끝난다)                   | 재시도하지 않고 `failed`(TR6이 `isRetryableError`에 421을 넣지 않았다)                           | 재시도 대상(TS12). 다른 풀 연결이 열려 있으면 `LIMIT`(TS13) |
| E7  | 새 클라이언트의 첫 전송에서 PASV 응답이 421                             | E4와 같은 감싼 오류, 마지막이 `'FTPError: 421 …'`                                                                         | `failed`                                                                                         | E6과 같다                                                   |
| E5  | 보조 로그인이 421                                                       | `FTPError`, `code: 421`                                                                                                   | 풀이 `isRetryableError`를 거치지 않고 `LIMIT`·`limitCap`로 처리(`TransferClientPool.ts:209-237`) | **그대로**                                                  |

해소되는 것: 한도 서버(R3 B, `max_cons = 4`)에서 짧은 몰림에 425를 받은 작업이 "Retry n/3"을 쓰고 몰림이 길면 `failed`로 끝나는 것(앞 문서 §9 위험 첫째), 그리고 세션 도중 421을 받은 작업이 곧바로 `failed`가 되는 것.

### 1-3. MCP 저장 서버 대상(④)

`connectionOf`(`agentTarget.ts:27-51`)는 저장 서버를 고르면 사용자가 같은 연결, 없으면 그 host·port의 유일한 연결을 돌려준다. 그래서 `ra`(저장 행 id 1의 사용자)가 끊기고 `rb2`만 연결돼 있으면 `server: 1`이 `rb2`로 간다(SH14, multi-connection R3 관찰 4). `disconnect({ server: 1 })`이면 `rb2`가 끊긴다. 둘 이상이면 `AMBIGUOUS: N connections match …`이다.
바뀐 뒤에는 사용자가 같은 연결만 고른다. 없으면 `NOT_CONNECTED`이고, 그 host·port에 다른 사용자의 연결이 있으면 그 키를 함께 알린다.

## 2. 핵심 결정 (R1)

`[사용자]`는 사람이 정한 것이고, 나머지는 이 문서가 그 결정을 코드에 대응시키며 근거와 함께 정한 것이다. `미결(권장안 적용)`은 권장안으로 진행하되 사람의 확인이 필요한 것이다(§10에도 모았다).

### 2.2 425·421을 풀 한도로 배우기(②·③)

| #    | 결정                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| TS7  | `[사용자]` **풀 클라이언트에서 난 425는 풀의 `LIMIT`처럼 다룬다.** 판정은 새 함수 `isLimitReply(err)`(`errorClassifier.ts`)다. 숫자 `code`가 425·421이거나, 메시지에 `Last error response was 'FTPError: 425 ` 또는 `'FTPError: 421 `가 들어 있으면 참이다. ## 4. 구현 함정

1. **정리는 `fail()`에서, 하지만 구간 항목은 빼고.** `fail()`은 구간 항목이면 `stopSegmented`를 부르고 그쪽이 지운다. 같은 작업을 새 경로가 또 지우면 `retryAfterClose`가 되살린 새 시도의 파일을 지울 수 있다. 조건은 `!item.segment && !item.borrow && job.direction === 'download' && this.opened.has(job)`이다.
2. **`onOpen`은 `openFd` 성공 직후, 첫 쓰기 전.** 열기가 실패하면(`EEXIST`·`EACCES`·`ENOENT`·`EISDIR`) 부르지 않는다. `downloadToFile`이 크기 0 파일을 지우면 `onRemoved`를 불러 큐가 `opened`에서 뺀다(§12 정정 3). 남겨 두면 재시도 대기 사이 그 경로에 생긴 남의 파일을 최종 실패가 지운다(TS3).
3. **배타적 다운로드의 `claim`.** `removePartial`은 지금처럼 `claim.created === false`면 지우지 않고, 지우면 `claim.created = false`로 돌린다(다음 시도는 `'wx'`). `opened`와 `claim`은 따로 둔다. GUI 다운로드에 `claim`을 주면 Test-630("GUI 다운로드는 claim 없음")이 깨지고 `'wx'` 의미가 섞인다(§6).
4. **`removePartial`의 결과.** 지금은 오류를 삼키고 `void`다. TS5를 위해 "지웠다·이미 없다·남았다"를 구별해야 한다. 취소 경로(`:572`)와 분할 경로(`:829`·`:841`·`:846`)의 호출은 결과를 쓰지 않으므로 동작이 바뀌지 않는다.
5. **TS7 ③은 `releaseAfterError` 대신이다.** `shrinkAfterLimitReply`가 `true`면 클라이언트는 이미 버려졌다. 다시 `releaseAfterError`·`discard`를 부르지 않는다. `false`면 클라이언트를 건드리지 않았으므로 지금처럼 `releaseAfterError`다. `leases.delete`·`finishRun` 순서(`:567-574`)는 그대로다(풀 계약: 반납 뒤 `running` 감소).
6. **`others`에 그 클라이언트를 넣지 않는다.** `discard` 전에 세면 혼자인 연결도 `others = 1`이 되어 TS9의 끝이 없어진다. 시험 로그인 중인 연결(`connecting`)은 센다.
7. **E4·E7의 클라이언트는 `FTPError`가 아니다.** 지금 `releaseAfterError`는 버린다. TS8은 어느 쪽이든 버린다. `isLimitReply`는 `instanceof FTPError`를 쓰지 않고 숫자 `code`로 본다(TR2와 같은 덕 타이핑).
8. **`RelayLane.run`의 임대 반납 순서.** 지금은 `for (const lease of leases.values()) lease.done(failure)`(`:309`)가 실패한 쪽을 고르기(`:327`) 전에 돈다. 실패한 쪽을 먼저 정한 뒤 그 임대에 안쪽 오류를 넘긴다. 성공·취소 때는 지금처럼 둘 다 `done(failure)`이다(취소면 `failure`는 닫힌 소켓 오류이고 `isLimitReply`가 아니다).
9. **통합 테스트는 실제 타이머다.** `maxDataChannels` 테스트는 `retrPace`로 전송이 겹치게 하고, 파일은 `SEGMENT_MIN`보다 작게 둔다(분할이 끼지 않게). 첫 전송은 새 클라이언트라 425가 E4 모양이다(EPSV 500 → PASV 425). `pool.limit`를 2로 고정해 확인하려면 모든 전송이 첫 시험 대기(2초) 안에 끝나게 `retrPace`를 고른다(예: 200 KiB를 64 KiB씩 150ms마다, 파일당 약 0.5초). 그러지 않으면 시험 로그인이 끼어 끝의 `limit`가 달라질 수 있다.
10. **`connectionOf`의 메시지에 비밀번호·저장 경로가 들어가지 않는다.** 키와 저장 행의 별칭·host·port·id·사용자만 쓴다(K4).

## 5. 기각한 대안

- **실패한 다운로드의 파일을 남겨 이어받기(REST)에 쓰기** — 지금 이어받기 경로가 없고(§1-1), 서버마다 REST 지원과 파일 변경 여부를 확인해야 하는 새 기능이다. 기각.
- **실패하면 `localPath`를 무조건 지우기(`opened` 없이)** — 덮어쓰기를 고른 기존 파일을, 열기에 실패했거나 시작도 못 한 작업이 지운다(TS3). 기각.
- **GUI 다운로드에도 `LocalFileClaim`을 주어 `created`로 판단하기** — Test-630이 고정한 "GUI는 claim 없음"과 `'wx'` 규칙이 섞인다. `onOpen` 인자 하나가 더 좁다. 기각.
- **로컬 다운로드에도 `partialRemoved`와 토스트** — 문구("on {{server}}")가 맞지 않아 새 i18n 키가 11개 로캘에 필요하다. 취소 정리도 알리지 않는다. 기각(미결, TS5).
- **425·421에 `limitCap`(로그인 421처럼 굳히기)** — 데이터 연결 다툼과 idle 시간 초과로도 오므로 재접속 전까지 느려진다. 기각(TS8·TS13).
- **425·421을 언제나 무료로 되돌리기(재시도 횟수를 전혀 쓰지 않기)** — 영구적인 425에서 끝나지 않는다. 기각(TS9).
- **425를 받은 클라이언트를 버리지 않고 다시 쓰기** — 그 제어 연결이 서버 슬롯을 계속 차지해 다음 데이터 연결도 거절된다. 기각(TS8 ①).
- **분할 구간에도 `LIMIT` 되돌림** — TS11. 기각(미결).
- **썸네일·폴더 미리보기 큐도 425로 동시 수 줄이기** — 앞 문서 TR7 후속(별도 기능)이다. 기각.
- **MCP에서 다른 사용자 연결이 하나면 그것을 쓰고 경고만 붙이기** — `disconnect({ server: id })`가 다른 계정을 끊는 문제가 남는다. `[사용자]`가 물러서기를 없애기로 했다. 기각(TS15).
- **`NOT_CONNECTED`에 연결된 모든 키를 늘어놓기** — 다른 호스트의 연결은 이 실패와 상관없다. 기각(미결, TS16).

## 10. 위험·미결·후속 과제

**미결(권장안 적용) — 사람 확인 필요**

- **TS5 로컬 정리는 알리지 않는다.** 지우지 못했을 때만 오류에 ` (partial file left on this computer)`를 붙인다. 다른 안은 서버 간 작업처럼 토스트를 띄우는 것이다(새 i18n 키 11개 로캘, `partialRemoved` 의미를 다운로드까지 넓힘).
- **TS11 분할 구간의 425는 지금 그대로다.** 구간은 한도를 배우지 않는다(시작이 0이 아닌 구간의 425는 한 스트림 재실행, 0인 구간은 구간 재시도). 다른 안은 구간에도 `LIMIT` 되돌림을 넣는 것이다.
- **TS16 `NOT_CONNECTED` 문구는 같은 host·port의 다른 사용자 키만 보인다.** 다른 안은 연결된 모든 키다.

**위험**

- **덮어쓰기를 고른 기존 파일은 실패하면 사라진다.** 첫 시도가 `'w'`로 연 순간 이미 잘렸으므로 지금도 원래 내용은 없다. 다만 "잘린 파일이 남는다"에서 "파일이 없다"로 바뀐다. 열기 전에 실패하면 남는다(TS3).
- **줄어든 `limit`는 그 세션의 처리량을 줄인다.** 데이터 연결 다툼이 끝나도 시험 로그인(2초부터 두 배, 성공해도 대기가 줄지 않음, TS8)으로만 되찾는다. 큐가 빈 뒤 10초(`POOL_IDLE_CLOSE_MS`) 또는 재접속이면 처음 값으로 돌아간다.
- **421 시간 초과도 `limit`를 줄인다(TS13).** idle 클라이언트를 집어 든 순간 서버가 421로 끊으면, 다른 풀 연결이 열려 있을 때 `limit`가 하나 준다. 시험 로그인으로 되찾는다.
- **425·421을 무료로 되돌리는 동안 작업 행은 `pending`이다.** "Retry n/3" 같은 사유가 보이지 않는다(풀 `LIMIT`와 같다). 긴 전송이 슬롯을 쥐고 있으면 오래 기다릴 수 있다.
- **MCP 동작이 바뀐다.** 지금까지 저장 서버 id로 다른 계정 연결을 쓰던 에이전트 흐름은 `NOT_CONNECTED`를 받는다. 문구가 넘길 키를 알려 준다.

**후속 과제(이번 범위 밖)**: 취소 정리에도 `opened`를 써서 "열기 전 취소"의 기존 파일을 남기기(TS6), 분할 구간의 한도 학습(TS11), 썸네일·폴더 미리보기 연결 수를 서버 한도에 맞춰 줄이기(앞 문서 TR7 후속), 죽은 서버 재시도 뒤 오류 문구가 FIN 원인을 잃는 것(앞 문서 §11 관찰 1), 무료 되돌림 중인 작업 행에 대기 사유 보이기, Windows 검증 호스트에서 (a)·(c) 재실측.

#### 정정 (사람 확인 필요)

1. **(c)에서 서버 간 작업의 다른 쪽 풀도 배웠다 → 고침.** 고치기 전 빌드의 첫째 번에 main 경고가 2번이었고, 그중 하나는 `RelayError: None of the available … 'FTPError: 425 …'`였다. TS10은 다른 쪽 임대에 `RelayError`를 넘기면 그 풀은 배우지 않는다고 보았지만, `RelayError`는 안쪽 오류의 문구를 그대로 옮겨 담으므로 감싼 응답(E4·E7)이면 `isLimitReply`의 정규식에 걸린다. 그래서 B의 425로 A의 풀까지 limit를 줄였다. `isLimitReply`의 감싼 응답 규칙을 basic-ftp가 만드는 평범한 `Error`(`Object.getPrototypeOf(err) === Error.prototype`)로 좁혔다(숫자 `code` 425·421은 그대로). 렌더러·도구 동작은 바뀌지 않는다. Test-1195(`TransferQueue.test.ts` 쪽)의 "그 밖(다른 오류)" 줄에 `done(new RelayError('dest', E4))`가 `false`이고 버린다는 확인을 더했다(고치기 전에는 RED). 고친 빌드로 (c)를 두 번 다시 돌려 경고는 B의 `Error: …` 1번뿐이었다. §3 대상 API의 `isLimitReply` 설명과 TS10의 괄호("그래서 다른 쪽 풀은 배우지 않는다")는 이 규칙으로 성립한다.
2. **Test-1187은 구현 전에도 GREEN이었다 → 고침.** 목 서버의 `finDuringRetr`는 첫 조각과 FIN을 거의 함께 보내 basic-ftp가 쓰기 전에 실패하므로, 매 시도의 로컬 파일이 0바이트이고 `downloadToFile`의 크기 0 정리가 이미 지운다. 그래서 `fail()`의 정리를 빼도 통과했다. 픽스처는 그대로 두고(TS14) 장면만 바꿨다. `finDuringRetr: 3`과 `retrPace`(16 KiB씩 150ms마다)로 넷째 시도가 바이트를 디스크에 쓰게 한 뒤 `server.close()`로 끊는다. 재시도 횟수가 다 찼으므로 그 오류는 최종 실패다. `fail()`의 `cleanUpLocal` 줄을 빼면 두 테스트 모두 RED(`localPath`가 남는다)임을 확인했다.
3. **크기 0 정리 뒤의 `opened` → 고침.** `downloadToFile`이 아무것도 받지 못한 빈 파일을 지워도 큐의 `opened`가 남아 있었다. 그러면 재시도 대기(2초)와 로그인 대기 사이 그 경로에 사용자나 다른 앱이 만든 파일을 `failPending` → `fail()`의 정리가 지운다(TS3 위반). `download`에 7번째 인자 `onRemoved`를 더해 크기 0 정리가 지운 뒤 부르고, 큐는 `opened`에서 뺀다(`claim.created = false`와 같은 자리). Test-1182 ③과 Test-1186의 끝 줄이 이를 고정한다(고치기 전에는 RED).
