# 핸드오프: 다중 FTP 연결 + 서버 간 스트림 전송

여러 서버에 **동시에** 연결해, 서로 다른 서버의 원격 탭을 함께 열고(분할 뷰의 좌우 포함) 서버 A의 파일을 서버 B로 직접 보낸다.
R1 결정은 `.omc/plans/explorer-v2-decisions.md`의 F절 마지막 항목과 G절 전체(사람과 합의)다. 이 문서가 그것을 구현 단위로 내린 **유일한 입력**이다.
이 문서에 없는 케이스는 완료 범위 밖이다. 케이스를 추가·병합·재해석하지 말 것.

작업 유형(R0): **기능(main 연결 구조 재편 + 렌더러 연결 상태 다중화) + 버그 수정 1건 + main 전송 기능 1개(서버 간 스트림 전송)**.
슬라이스(§13) S0~S5b를 순서대로 진행하고, 슬라이스마다 그 슬라이스의 테스트를 먼저 세워 RED를 본 뒤 GREEN으로 만든다. 각 슬라이스 끝에 앱이 그대로 동작해야 한다. 끝으로 실제 앱에서 R3 실측(§14)을 한다.

이웃 스펙(같은 날 병렬로 작성, 범위가 겹치지 않는다):

- `docs/handoff/split-view.md`(Test-1040~1099) — 탭 드래그 분할 뷰. **이 문서의 §2 MC8 `viewerId` 계약과 MC11 탭별 게이트를 그대로 쓴다.** 분할 뷰 자체(패널·구분선·오버레이·활성 패널)는 이 문서의 범위가 아니다.
- `docs/handoff/explorer-menu-and-focus.md`(Test-846~869), `docs/handoff/shelf-os-drop.md`(Test-870~889), `docs/handoff/collapsible-sidebars.md`(Test-890~919), `docs/handoff/file-category-filter.md`(Test-920~959) — 이 문서와 같은 파일(`Sidebar.tsx`·`Explorer.tsx`·`dnd.ts`)을 고칠 수 있다. 충돌은 §13의 병합 규칙을 따른다.

## 1. 바꾸는 것

지금 main은 `FtpConnectionManager` **하나**(`src/main/ipc/ftpHandlers.ts:49`)를 모든 서비스가 공유한다. 전송 큐·풀(`transferHandlers.ts:43`), 썸네일 큐(`thumbnailHandlers.ts:25`), 폴더 미리보기 큐(`galleryHandlers.ts:60`), 큰 미리보기(`previewHandlers.ts:44`), 드래그(`dragHandlers.ts:24`), MCP 도구(`src/main/index.ts:142-156`)가 모두 그 하나를 쥔다.
렌더러는 `useFtpStore`의 단일 `connectionStatus`·`host`·`port`·`username`(`useFtpStore.ts:21-26`)으로 "지금 서버"를 판단하고, 다른 서버의 원격 탭은 목록 대신 "다른 서버" 패널(`Explorer.tsx:124-133`의 gate `'other'`)을 보인다.

바뀐 뒤:

```
main
 ConnectionRegistry  Map<ConnKey, FtpSession>                       (신규 src/main/ftp/ConnectionRegistry.ts)
   FtpSession { key, manager: FtpConnectionManager, fileOps, pool, queue: TransferQueue,
                thumbs: ThumbnailQueue, gallery: RemoteGalleryPreviewQueue }
 TransferHub  세션 큐들의 집계 + 서버 간 전송(RelayLane)             (신규 src/main/transfer/TransferHub.ts, RelayLane.ts)
 공유: DB, CacheManager, ThumbnailGenerator, RemoteFolderPreviewCache, PreviewCacheManager, OperationManager, LocalFileSystem
 IPC: 원격 채널은 첫 인자 conn(ConnKey). 이벤트 페이로드·TransferJob·OperationJob에 server

renderer
 useFtpStore.connections: Record<ConnKey, { status, host, port, user, error }>
 탭마다 게이트: 그 탭의 loc.server 연결 상태로 live / connecting / stale / lost / offline
 사이드바·상태 표시줄·툴바가 서버별, 저장 비밀번호 서버는 탭이 보일 때 자동 연결
 원격→원격(다른 서버) = 서버 간 스트림 전송(RETR → PassThrough → STOR, 임시 파일 없음)
```

해소되는 기존 버그(B1): 툴바에서 다른 서버로 연결하면 `useServerStore.connect`가 먼저 끊는다(`useServerStore.ts:158-160`). 큐는 매니저 하나를 공유하므로, 대기 중이던 전송 작업이 **새 서버에서** 실행된다(경로만 같은 엉뚱한 파일을 받거나 올린다). 다중 연결에서는 선행 끊기를 지우고, 작업은 그 작업의 연결(`TransferJob.server`) 큐에서만 돈다.

### 4.3 `viewerId` 계약 (split-view.md가 쓴다)

1. `viewerId`는 그리드를 그리는 패널의 안정된 id(1~64자)다. 분할 뷰 전에는 `MAIN_VIEWER`. 한 패널은 수명 동안 같은 id를 쓴다.
2. `thumbnail:requestBatch(conn, viewerId, reqs)`는 **그 `(conn, viewerId)`의 직전 배치만** 교체한다: 직전 배치에 있었고 이번에 빠졌으며 아직 시작하지 않은 항목은, **다른 뷰어의 현재 배치에도 없을 때만** 버린다. 다른 뷰어가 원하는 항목은 남는다(우선순위는 원하는 뷰어들 중 가장 작은 값).
3. `thumbnail:cancelAll(conn | null, viewerId)`는 그 뷰어의 배치를 잊고, **그 뷰어만 원하던** 대기 항목을 버린다. 다른 뷰어의 대기·진행 항목은 그대로 두고 클라이언트를 닫지 않는다. 그 세션에 다른 뷰어의 배치가 하나도 남지 않으면 **지금과 똑같이** 전부 취소한다(대기·단건 비우기, 클라이언트 닫기, 세대 증가 — `ThumbnailQueue.ts:117-127`, Test-269·270).
4. 패널의 원격 위치가 바뀌면(서버가 바뀌는 경우 포함) 패널은 새 배치 **전에**(`useLayoutEffect`) `cancelAll(null, viewerId)`와 `gallery:cancelAll(null, viewerId)`를 보낸다(thumbnail-viewport-priority D14 순서 유지). 패널이 사라질 때도 같은 두 호출을 보낸다.
5. 폴더 미리보기 대기 항목은 소유 뷰어 집합을 가진다. `gallery:cancelAll(conn | null, viewerId)`는 그 뷰어를 집합에서 빼고, 집합이 빈 항목만 `'Cancelled'`로 거절한다. 같은 폴더를 두 뷰어가 기다리면 한쪽 취소로 다른 쪽의 promise가 거절되지 않는다. 세션에 남은 소유가 없으면 지금처럼 클라이언트를 닫는다.
6. 단건 `thumbnail:request(conn, req)`는 뷰어가 없다. 3의 "전부 취소" 때만 버려진다(explorer-shelf §15의 D30 위험과 같다).

## 5. 서버 간 전송 실행 (MC23~MC28 상세)

한 서버 간 작업 `job`(`direction: 'relay'`)의 한 시도:

1. `RelayLane`이 실행 중인 작업 수 < `MAX_RELAY_RUNNING`일 때 `pending` 작업을 FIFO로 꺼낸다.
2. 두 세션이 모두 `connected`가 아니면 MC25 규칙의 오류 `'Not connected'`(그 서버 접두어)로 처리한다.
3. `[first, second] = [sourceServer, server].sort()` 순서로 `queueOf(first).borrow(signal)` → `queueOf(second).borrow(signal)`. 어느 쪽이든 `null`이면 MC28(재시도 없음, 이미 빌린 쪽은 `done()`으로 돌려준다).
4. `job.status = 'active'`, `startedAt`. 받는 쪽 사이 폴더: 배치 메모(`BatchDirs`, `TransferQueue.ts:61-64`와 같은 형태, 레인이 작업별로 `WeakMap`에 보관)로 받는 쪽 클라이언트에서 `MKD`(`ensureRemoteDir`과 같은 음수 응답 허용).
5. `relayOnce(src, dst, sourcePath, remotePath, onProgress)`:
   - `pass = new PassThrough({ highWaterMark: RELAY_BUFFER_BYTES })`, `gate` = `pass`로 쓰기를 넘기되 **`end()`를 넘기지 않는** Writable(§8-1).
   - `up = dst.uploadFrom(pass, remotePath)`, `down = src.downloadTo(gate, sourcePath)`를 함께 시작. `dst.trackProgress((i) => onProgress(i.bytesOverall))`.
   - `down` 이행 **그리고** `gate`의 `'finish'` 뒤에만 `pass.end()`. `down` 거절이면 `pass.destroy(err)` + `dst.close()`. `up` 거절이면 `src.close()`.
   - 둘 다 이행해야 성공. 먼저 난 오류와 그 쪽 서버(`src`면 `sourceServer`, `dst`면 `server`)를 돌려준다.
6. 성공: `transferredBytes = totalBytes`, `completed`, 두 빌림 `done()`(release). 받는 쪽 세션 `manager.emit('mutation', { kind: 'upload', remotePath })`(GUI 목록 갱신, 일반 업로드와 같다).
7. 실패: 두 빌림 `done(err)`(discard). MC25 재시도 또는 `failed` → `failed`면 MC26 부분 정리. 정리는 이번 시도에서 받는 쪽 진행 바이트가 1 이상일 때만 `deleteFile`을 부르고, 그것이 이행하면 `job.partialRemoved = true`, 거절하면 `job.error`에 접미사. 표시·접미사는 정리가 끝난 뒤의 `queue:updated`로 따로 나가도 된다(렌더러는 `partialRemoved`가 처음 나타나는 순간만 본다, §10).
8. 취소(`hub.cancel(id)`): `pending`이면 `signal.abort()` → `cancelled`(정리 없음, `partialRemoved` 없음). `active`면 두 클라이언트 `close()` → 5가 거절 → 상태가 이미 `cancelled`이므로 재시도하지 않고 7과 같은 MC26 부분 정리.
9. 세션이 끊기면(`connecting`·`disconnected`) 그 풀이 클라이언트를 모두 닫는다(`TransferClientPool.ts:124-135`) → 5가 거절 → MC25. 이후 빌림은 그 큐의 로그인 실패 경로로 거절된다 → 결국 `failed`.

진행·상태 알림은 레인이 허브의 `queue:updated`로 `FLUSH_MS`(100ms) 주기로 묶어 낸다(큐와 같은 형식 `TransferUpdate`).

## 8. 구현 함정

1. **basic-ftp는 `downloadTo(Writable)`의 대상을 실패해도 `end()`한다**(`node_modules/basic-ftp/dist/Client.js:504-508`, 6.2.0의 `finally { destination.end() }`). `PassThrough`를 그대로 넘기면 RETR가 중간에 끊겨도 STOR가 EOF를 받아 **잘린 파일로 정상 완료**한다. 반드시 `end()`를 넘기지 않는 `gate` Writable을 넘기고, 다운로드가 이행하고 `gate`의 `'finish'`(남은 쓰기가 모두 `pass`로 간 뒤)가 온 다음에만 `pass.end()`. Test-986이 이 동작을 흉내 낸 가짜 클라이언트로 고정한다.
2. **교착.** 두 슬롯을 빌리는 순서가 작업마다 다르면 A→B와 B→A가 서로를 기다린다(각 서버 한도 1이면 바로 재현). 늘 ConnKey 오름차순(MC24, Test-985).
3. **빌린 슬롯은 큐의 `running`에 들어가야 한다.** 레인이 풀의 `acquire()`를 직접 부르면 큐는 슬롯이 빈 줄 알고 `acquire`가 `LIMIT`을 돌려줄 때 `running === 0`이면 바로 다시 `pump`한다(`TransferQueue.ts:403-411`) — 빈 루프가 돈다. `borrow()`는 큐의 `WorkItem`으로 줄 서고, 반납(`done`)은 `finishRun()`(`:921`)을 거친다.
4. **썸네일 핸들러와 세션 팩토리의 순서.** 지금 `registerThumbnailHandlers`가 `CacheManager`·`ThumbnailGenerator`를 만든다(`thumbnailHandlers.ts:22-23`). 세션 팩토리가 그것을 써야 하므로 `index.ts`에서 공유 객체를 먼저 만들고 레지스트리를 만든다. MCP 미리보기도 같은 공유 객체를 쓴다(Test-464·474의 전제).
5. **캐시 키는 main과 렌더러를 같은 슬라이스(S2)에서 바꾼다.** 한쪽만 바뀌면 `thumbnail:ready`의 키가 렌더러 스토어와 맞지 않아 썸네일이 영원히 대기로 보인다(오류도 없다). Test-999가 같은 입력에 두 함수가 같은 문자열을 내는지 본다.
6. **S1의 렌더러 어댑터.** S1에서 핸들러가 `conn`을 첫 인자로 받으므로 렌더러 호출부도 S1에서 `conn`을 붙인다. 값은 아직 "지금 연결 하나"(`currentConn()`, S1 임시 헬퍼)다. S2가 그것을 `loc.server`·`entry.server`로 바꾸고 `currentConn()`을 지운다. 위치 인자라 "있으면 쓰고 없으면 지금 연결" 같은 겸용 핸들러는 두지 않는다(경로 문자열과 키를 추측으로 가려야 한다).
7. **`registry.connect`의 멱등성.** 이미 `connected`인 키에 `manager.connect`를 다시 부르면 `emitStatus('connecting')`이 풀·썸네일·미리보기 큐를 모두 비운다(`TransferClientPool.ts:124-131`, `thumbnailPreviews.ts:53-60`). 자동 연결·에이전트 `connect`·툴바가 같은 서버를 다시 이을 수 있으므로 레지스트리가 막는다(Test-963).
8. **`FtpConnectionManager`의 이벤트는 키를 모른다.** `emitStatus`(`FtpConnectionManager.ts:260-264`)·`mutation`(`FtpFileOperations.ts:179` 등)은 그대로 두고, 레지스트리가 세션을 만들 때 구독해 `server`·`host`·`port`·`user`(키에서)를 붙여 다시 낸다. 풀(`TransferClientPool.ts:139`)·미리보기는 지금처럼 자기 매니저의 이벤트를 직접 듣는다.
9. **`ftp:connectionStatus` 구독 위치.** 지금 `TabExplorer`가 구독한다(`Explorer.tsx:224-230`). 분할 뷰는 탐색 영역이 둘이라 두 번 받는다(결과는 같지만 낭비). S3에서 `AppShell`의 훅 하나로 옮긴다. 탭이 하나도 없을 때도 사이드바·상태 표시줄이 상태를 받는다(Test-1033).
10. **자동 연결의 계기는 "보이기 시작"뿐이다**(MC12). 상태가 `disconnected`로 바뀌는 것에 반응하면 사용자가 끊는 순간 다시 잇는다. 계기는 `useEffect(…, [tab.id, loc.server])`(탐색 영역 마운트·서버 변경)이고, 그 시점에 상태를 한 번 읽는다. 같은 키에 `connecting` 중이면 부르지 않는다(분할 뷰 두 패널이 같은 서버를 보일 때 한 번만, Test-1034).
11. **사이드바의 저장 안 된 연결.** 지금은 `live` 하나만 맨 위에 그린다(`Sidebar.tsx:230-232`). `connections`의 모든 키 중 저장 행의 키와 다른 것을 그린다. 끊긴(`disconnected`) 저장 안 된 연결은 그리지 않는다(돌아갈 곳이 최근 위치에 있다, Test-1034).
12. **`TransferJob.server`가 필수 타입이 된다.** 렌더러 테스트의 작업 픽스처(§7)를 함께 고친다. 큐 생성자 옵션이 없으면 `''`이므로 main의 기존 큐 테스트는 그대로다.
13. **`planSend`의 같은 쪽 검사 두 가지는 같은 서버 항목에만 한다.** "자기 안으로"(`sendPlan.ts:58-59`)와 "이미 여기 있음"(`:60`, `here++`)은 둘 다 **경로만** 견준다. 원격 항목은 `e.server === dest.server`일 때만 이 두 검사를 하고, 서버가 다르면 바로 `relay`로 보낸다. 그렇지 않으면 A의 `/photos/x.jpg`를 B의 `/photos`로 보낼 때 "이미 여기"로 세어 보내지 않고, 모든 항목이 그렇다면 `send.invalidHere`로 막힌다(같은 폴더 구조의 서버 사이 복사가 주된 쓰임이라 자주 일어난다). 서버가 다르면 `/a`를 서버 B의 `/a/b`로 보내는 것도 유효하다(Test-1016).
14. **MCP 마지막 사용 연결은 앱 전역**이다. 두 에이전트가 동시에 쓰면 서로의 기본 대상을 바꾼다. 2개 이상 연결된 상태에서 인자 없이 부르면 `AMBIGUOUS`가 나는 쪽이 안전하므로, ②는 "마지막 사용 연결이 여전히 연결됨"일 때만이다. 8개 도구의 `server` 속성 설명과 서버 `INSTRUCTIONS`에 "Pass server when more than one server is connected"를 넣는다(Test-1008).

## 9. 기각한 대안

- **`FtpConnectionManager`를 다중 연결 클래스로 키우기** — 모든 서비스가 매니저의 단일 상태(`_host`·`_config`·`client`)에 기대고 있어 메서드마다 키를 받게 된다. 연결 1개 단위로 두고 레지스트리로 묶는 쪽이 기존 테스트(Test-291 등)를 그대로 지킨다. 기각(결정 파일 G).
- **전송 큐 하나에 연결 키를 넣기** — 풀이 연결마다 따로라 한도·`LIMIT`·로그인 실패 처리를 키별로 쪼개야 한다. 큐·풀을 세션마다 두고 허브로 묶는다. 기각.
- **서버 간 전송을 받는 쪽 큐의 작업으로 넣기** — 받는 쪽 슬롯을 쥔 채 보내는 쪽 슬롯을 기다려 교착(§8-2)과 빈 루프(§8-3)가 생긴다. 레인이 순서대로 두 슬롯을 빌린다. 기각.
- **임시 파일을 거치는 "받았다 올리기"** — 디스크 공간·정리 코드가 필요하고 두 번 쓴다. 사람이 스트림 직결로 정했다. 기각(MC23).
- **서버 간 재시도를 받은 바이트부터 이어 하기(REST + APPE)** — 서버마다 APPE·REST 지원이 다르고, 보내는 쪽 REST 무시를 감지하는 코드(분할 다운로드의 것)를 또 만들어야 한다. 처음부터 다시(사람이 정함). 기각.
- **서버 간 실패 시 부분 파일을 늘 남기기(지금 업로드와 같게)** — 덮어쓰기 대상이면 원본처럼 보이는 잘린 파일이 남는다. MC26(미결).
- **보조 연결 불가 서버에서 메인 클라이언트로 서버 간 전송** — 그 서버의 탐색이 전송 내내 멈추고 취소할 수 없다. 기각(MC28).
- **`thumbnail:cancelAll`을 뷰어 구분 없이 유지하고 분할 뷰가 피하기** — 두 패널이 같은 서버를 보면 피할 방법이 없다. 기각(MC8).
- **`folder_previews`에 `username` 열을 더하기** — 테이블 제약 `UNIQUE(host, port, folder_path)`를 바꿀 수 없어 두 사용자의 같은 경로가 충돌한다. 테이블을 다시 만들려면 옛 테이블을 지워야 한다(추가만 허용). 새 테이블. 기각(MC9).
- **유휴 연결 자동 해제, 연결 수 상한** — 사람이 "없음"으로 정했다. 기각.
- **에이전트마다 대상 연결 기억** — MCP 요청마다 새 `McpServer`이고 agent-access가 세션 고정을 지웠다. 앱 전역 하나 + `AMBIGUOUS`. 기각(MC18).
- **`ftp:connect`가 키를 돌려주기** — 렌더러가 같은 함수(`connKey`)로 만들 수 있고, 반환 형태를 바꾸면 연결 UI 테스트의 목을 모두 고쳐야 한다. 기각.

### R3에서만 확인되는 것

jsdom·가짜 클라이언트로는 다음을 볼 수 없다(§14에서 확인): 실제 두 FTP 서버 사이 스트림의 역압·속도와 파일 해시 일치, basic-ftp 실제 `end()` 동작에서 잘린 파일이 완료되지 않음, 서버 프로세스를 죽였을 때의 실제 오류 경로, preload를 거친 IPC 인자 형태(렌더러 테스트는 `window.api` 목), 임시 폴더에 파일이 생기지 않음, 두 서버 동시 썸네일·같은 경로 썸네일 분리, 자동 연결의 실제 저장 비밀번호 복호화.

## 15. 위험·미결·후속 과제

**미결(권장안 적용) — 사람 확인 필요**

- **MC12 자동 연결 계기**: "탭이 보이기 시작할 때"만. 보이는 탭의 서버를 끊으면 그 자리에서 다시 잇지 않고, 다른 탭에 갔다 돌아오면 다시 잇는다.
- **MC19 `connect`의 `BUSY` 삭제**: 이미 연결된 서버면 재로그인 없이 성공, 다른 서버는 건드리지 않으므로 `BUSY`가 필요 없다. 결정 파일의 "refuseIfBusy 해당 연결만"은 `disconnect`에만.
- **MC26 서버 간 부분 파일 정리**: 취소·최종 실패 때 받는 쪽에 1바이트 이상 썼으면 지운다(같은 쪽 업로드는 지금처럼 남긴다).

**위험**

- **IPC 인자 형태는 렌더러 테스트가 잡지 못한다**(목 `window.api`). S1·S2의 호출부 누락은 개발 앱과 R3 (a)·(j)로만 걸러진다.
- **느린 받는 쪽**: 역압으로 보내는 쪽 데이터 소켓이 30초 넘게 멈추면 basic-ftp 시간 초과로 보내는 쪽이 실패한다(재시도로 처음부터). 아주 느린 업로드 대상과 빠른 원본 사이에서 대용량 서버 간 전송이 반복 실패할 수 있다.
- **서버 간 대량 배치는 양쪽 큐의 슬롯을 함께 쓴다**(최대 4개씩). 그동안 두 서버의 일반 전송이 느려진다.
- **세션은 지우지 않는다**(MC5). 한 실행에서 수십 개 서버에 연결하면 끊긴 세션 객체(큐·풀·썸네일 큐, 연결은 닫힘)가 남는다. 메모리만 쓴다.
- **에이전트 마지막 사용 연결은 앱 전역**(§8-14).
- **옛 썸네일 캐시**: 키 형식이 바뀌어 첫 방문 때 썸네일을 다시 만든다(옛 행은 LRU로 사라진다). 옛 `folder_previews` 행은 남는다.
- **같은 호스트·포트, 다른 사용자**: 저장 서버 행은 `host, port`로 하나뿐이라(`idx_servers_host_port`, `database.ts:99`) 사이드바에는 저장된 계정 하나와 "저장 안 된 연결" 행으로 보인다.

**후속 과제(이번 범위 밖)**: 분할 뷰(split-view.md, S6), 연결 수 상한·유휴 해제, 탭 복원(explorer-shelf D23), 서버 간 이어 보내기(REST/APPE), 옛 `folder_previews` 테이블 정리, 에이전트별 대상 연결, 같은 서버 안 복사.
